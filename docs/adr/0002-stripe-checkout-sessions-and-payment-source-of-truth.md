# Stripe Checkout Sessions for Payment Links; a completed payment always overrides manual Payment Status

A Payment Link is created as a fresh Stripe Checkout Session per Registration, tagged with that Registration's Trip and Participant in its metadata, rather than using Stripe's own "Payment Links" product (a small number of reusable links normally created once in the Stripe dashboard and shared broadly). We considered the dashboard product first since it needs no integration code, but rejected it: a Checkout Session created via the API can carry the exact Registration it belongs to in its metadata, which the webhook needs to know which Registration to mark Paid. Checkout Session is the primitive meant for "the server creates a fresh one-off checkout tied to a specific record," which is exactly this shape.

When the webhook receives a successful payment for a Checkout Session, it sets that Registration's Payment Status to Paid unconditionally — even if a Staff or Admin member manually set a different Payment Status after the link was sent (for example, marked it Refunded, or cancelled the Registration entirely). We considered having a manual change lock out the later automatic update, but rejected it: if money has actually moved through Stripe, the system's record should say so. Any resulting inconsistency (e.g. a cancelled Registration that still ends up Paid) is a real reconciliation Staff need to see and act on — the system should surface it, not silently suppress the payment confirmation to keep the record tidy.
