# Stripe Checkout Sessions for Payment Links; a completed payment always overrides manual Payment Status

A Payment Link is created as a fresh Stripe Checkout Session per Registration, tagged with that Registration's id in its metadata, rather than using Stripe's own "Payment Links" product (a small number of reusable links normally created once in the Stripe dashboard and shared broadly). We considered the dashboard product first since it needs no integration code, but rejected it: a Checkout Session created via the API can carry the exact Registration it belongs to in its metadata, which the planned completion webhook will need to know which Registration to mark Paid. Checkout Session is the primitive meant for "the server creates a fresh one-off checkout tied to a specific record," which is exactly this shape.

Once a completion webhook exists, it is intended to set a Registration's Payment Status to Paid unconditionally on a successful payment — even if a Staff or Admin member manually set a different Payment Status after the link was sent (for example, marked it Refunded, or cancelled the Registration entirely). We considered having a manual change lock out that later automatic update, but decided against it: if money has actually moved through Stripe, the system's record should say so. Any resulting inconsistency (e.g. a cancelled Registration that still ends up Paid) is a real reconciliation Staff need to see and act on — the system should surface it, not silently suppress the payment confirmation to keep the record tidy. Until that webhook ships, Payment Status still only changes by hand.
